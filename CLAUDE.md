# Folio (Personal Finance Webapp)

A personal finance webapp for a single user (me), called Folio: password-gated login, expense tracking, a wishlist, and recurring monthly payment tracking.

## Decided stack

* Frontend and backend: Next.js (App Router) with TypeScript
* Styling: Tailwind CSS is installed but the app doesn't use its utility classes — every component uses hand-authored CSS (`globals.css` for page-level/shared classes, a `components.module.css` per-directory for scoped ones), matching a specific soft-sage/warm-yellow palette defined as CSS custom properties. Match this palette and pattern for new UI; don't introduce Tailwind utility classes or a different color system.
* Database and auth: Supabase (Postgres, email/password auth through Supabase Auth, Row Level Security)
* Validation: Zod on all incoming form and API data, backed by database constraints
* Hosting: Vercel (Hobby plan) for the app, Supabase for the database and auth
* Charts: Recharts (`src/components/dashboard/wallet-distribution-chart.tsx` is the first real usage; `spend-chart.tsx` predates that decision and is hand-rolled SVG — leave it as is rather than migrating it speculatively)
* Icons: `lucide-react` for anything data-driven (category icons, looked up by a kebab-case string key stored in the database via `src/components/ui/category-icon.tsx`); the original hand-drawn SVG set in `src/components/ui/icon.tsx` stays for fixed chrome (nav, buttons) since it already matches the exact stroke width/style
* No UI component library (no Radix, no Headless UI): dialogs use the native `<dialog>` element (`src/components/ui/modal.tsx`), the custom dropdown (`src/components/ui/select.tsx`) is hand-rolled. Keep this pattern; a single-purpose UI library isn't worth the dependency at this app's size.

Do not propose alternative stacks or re-open this decision.

Auth history: originally planned as Google OAuth, then switched to Supabase magic link, then switched again to Supabase email/password. There is still no public registration: the single owner account is provisioned directly against Supabase (admin API or dashboard), never through a sign-up form. `/register` must not exist as a route.

## Prerequisites

1. A Supabase project with the Email provider enabled for password sign-in (no external OAuth provider needed)
2. A GitHub repository for the project (already set up: `github.com/aeomantic/FinanceWebApp`)
3. Environment variables in `.env.local` (gitignored, see `.env.example`):
   * `NEXT_PUBLIC_SUPABASE_URL`
   * `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   * `SUPABASE_SERVICE_ROLE_KEY` (server-only, never exposed to the client, not used by any request-serving code path — only for one-off admin scripts like provisioning the owner account)
   * `ALLOWED_EMAIL` (the only email allowed to log in)

## Data model

See `supabase/migrations/` for the schema as SQL migration files, applied in order. Do not apply schema changes by hand through the dashboard; commit a migration file instead. Migrations that need to land on the live project get pasted into the Supabase SQL Editor manually — there is no working CLI link to this project (the local `supabase` CLI login is tied to an unrelated project), and no DB password for a direct connection.

**Two migrations are committed but not yet confirmed applied to the live project: `20260915000000_settings.sql` (profile `display_name`/`theme_preference`, plus the `set_default_wallet`/`delete_managed_wallet` functions `dashboard/actions.ts` now calls) and `20260915010000_recurring_commitments.sql` (the BNPL/subscription columns on `recurring_rules`, its validation trigger, and its RLS policies).** Paste both into the Supabase SQL Editor, in that order, before using Settings or Commitments against the real account — until then `getSettingsData()`/`getCommitmentsData()` surface a friendly "apply the latest database update" error rather than crashing, and `renameWallet`/`setDefaultWallet`/`deleteWallet` in `dashboard/actions.ts` will fail (they now call the Postgres functions the first migration adds).

Tables: `profiles`, `wallets`, `categories`, `transactions`, `wishlist_items`, `recurring_rules`, `recurring_occurrences`.

The ledger is wallet-based (envelope style): every transaction moves money into, out of, or between wallets, not just into a category. This was a deliberate pivot from the original "categories on bare transactions" design (see `supabase/migrations/20260914053049_add_wallets_ledger_model.sql`).

* `wallets`: named balances (`balance_minor`) the owner tracks separately, e.g. "Everyday", "Food & Groceries", "Bills". Each has its own currency.
* `categories`: narrowed to `type` in (`expense`, `income`) — transfers are a transaction type now, not a category. Has `icon` for the picker UI, plus the original `color`/`is_archived`.
* `transactions`: `wallet_id` (required), `destination_wallet_id` (only for `type = 'transfer'`), `category_id` (nullable, `on delete set null`), `amount_minor` (positive magnitude, direction comes from `type`), `note` (replaces the old separate `merchant`/`notes` fields).
* A Postgres trigger (`sync_wallet_balance`) keeps `wallets.balance_minor` correct on every transaction insert/update/delete, so the balance is derived from the ledger rather than trusted from a second client-side write.
* RLS on `transactions` also verifies `wallet_id`/`destination_wallet_id`/`category_id` belong to the caller, not just `user_id` — otherwise a request could satisfy `user_id = auth.uid()` while still pointing at (and mutating the balance of) another user's wallet.
* `wallets.is_default` marks the one wallet the dashboard selects on load; a partial unique index (`wallets_one_default_per_user`, `where is_default`) enforces at most one per user at the database level. The first wallet a user creates becomes their default automatically (`createWallet` in `src/app/dashboard/actions.ts`); `setDefaultWallet` clears the old one before setting the new one, in that order, since a partial unique index only rejects two `true` rows, never zero.

**This project's live RLS policies have repeatedly not matched what the committed migration files assumed.** Phase 0's schema turned up already applied to the live project before any migration was run against it (never fully explained), and after the wallets migration landed, `transactions` INSERT, UPDATE, and SELECT policies plus all four `categories` policies turned out to be missing, misnamed, or otherwise not doing what the original migration specified — causing writes or reads to silently fail (no error, RLS just filters to zero rows) rather than throw. The fix pattern each time: `select policyname from pg_policies where schemaname = 'public' and tablename = '<table>'`, drop whatever actually exists via a `do $$ ... $$` block, recreate cleanly — never assume a policy exists under the name a migration file gives it. If something silently returns empty or a write silently no-ops against the live database, suspect RLS policy drift before anything else, and diagnose by reproducing the same operation with the service-role key (bypasses RLS) to isolate schema/payload issues from RLS issues.

Notes on the rest of the schema:

* Money is always an integer in minor units. `amount_minor = 1250` means SGD 12.50. Never use a float or JS number for stored money.
* Every table carries `user_id` even though there is one user. This keeps RLS simple and future-proofs the schema.
* A wishlist item links to a transaction only after purchase, through `purchased_transaction_id`. Wishlist and transactions stay separate: one is intent, the other is fact.
* Recurring payments follow a rule-plus-occurrences pattern, not full RRULE syntax. Five frequency values are sufficient for v1: weekly, monthly, quarterly, yearly, custom_months. Not started yet; when it is, decide how recurring bills interact with the narrowed category `type`.
* Row Level Security is enabled on every table, with policies restricting select, insert, update, and delete to rows where `user_id = auth.uid()`.

## Build order

Work through phases one at a time. After each phase, stop, summarize what was built, and wait for confirmation before starting the next one. (Note: a large chunk of Phase 2/3 landed in one uncoordinated pass outside this discipline — see status below. Return to one-phase-at-a-time from here forward.)

* Phase 0: Scaffolding — done. Next.js/TypeScript, Tailwind, Supabase clients (browser + server), env vars, repo pushed to GitHub.
* Phase 1: Authentication — done. Email/password sign-in through Supabase Auth (`/login`, `/forgot-password`, `/auth/reset-password`). Allowlist enforced server-side at session creation and re-checked on every request via the proxy, not just hidden in the UI. No registration route; the owner account is provisioned via the admin API.
* Phase 2: Wallets, categories, and transactions — partially done. `src/app/dashboard/actions.ts` has `createWallet`, `createCategory`, `setDefaultWallet`, `renameWallet`, `deleteWallet`, and a transfer-aware `recordTransaction` (expense/income/transfer, wallet-scoped, optional category, `note`). Category creation is available inline from the transaction form via a custom dropdown (`src/components/ui/select.tsx`), not a native `<select>`. A standard 10-expense/6-income category taxonomy was originally seeded automatically on first dashboard load whenever the account had zero categories; that auto-reseed was removed once Settings could delete categories (see below), since re-seeding on every empty read meant a deliberate "delete all categories" was silently undone on the next page load. `getDashboardData()` now reads categories as-is and never recreates them — dead code from that removal (`DEFAULT_CATEGORIES`/`src/lib/dashboard/default-categories.ts`) was deleted rather than left orphaned. This is safe for the single real account this app runs against (already seeded from earlier development); a genuinely fresh Supabase project would need categories added by hand or a new seeding path reintroduced deliberately. Every wallet card (in `WalletList` and the `/wallets` page's balance grid) has a three-dot action menu (`src/components/dashboard/wallet-card-menu.tsx`, built on a hand-rolled `role="menu"` component, `src/components/ui/dropdown-menu.tsx` — distinct from `select.tsx`'s listbox pattern since menu items trigger actions rather than binding a value): set/see default, rename, hide balance, delete. Deleting a wallet is a real, irreversible action — `transactions.wallet_id` is `on delete cascade`, so it takes every transaction on that wallet with it; `deleteWallet` refuses to delete a user's only wallet and auto-promotes another wallet to default first if the one being deleted was it. Per-wallet balance-hiding is a display preference, not account data, so it lives in localStorage (`src/lib/dashboard/use-hidden-wallets.ts`, via `useSyncExternalStore` so every mounted instance stays in sync and SSR gets a stable empty snapshot) rather than a database column. Wallet creation lives in one shared `AddWalletDialog` (`src/components/dashboard/add-wallet-dialog.tsx`), taking the trigger markup as a render prop (`children: (open) => ReactNode`) so `WalletList`'s "+" tile and the `/wallets` grid's full-width "Add wallet" card share the same form/validation logic; it opens/closes via `isOpen` state plus a `useEffect` calling `showModal()`/`close()` (matching `modal.tsx`'s pattern) rather than an imperative ref call from the trigger callback, since the latter tripped the `react-hooks/refs` rule (a ref-closing closure passed into a render prop can't be proven safe from render-time access). The horizontal wallet carousel (`WalletList`, used on `/dashboard`) hides its scrollbar cross-browser (`scrollbar-width: none`, `-ms-overflow-style: none`, `::-webkit-scrollbar { display: none }` — the earlier `scrollbar-width: thin` left a visible thumb cutting across the bottom of the cards) and widens each card to a 170px minimum with a wrapping (not truncating) name, so names like "Food & Groceries" render in full instead of ellipsizing to "Food & Groceri...". The three-dot menu is a real `<button>` for wallet selection plus a separately absolutely-positioned `WalletCardMenu` in the corner, rather than the whole card being one clickable surface with the menu nested awkwardly inside it. The bottom mobile nav is a single shared `MobileNav` component (`src/components/dashboard/mobile-nav.tsx`), used by both the dashboard shell and the wallets page, with active-state styling keyed off `usePathname()`: Home is a solid black circle whose house icon turns `#fef38b` when active (i.e. not on `/wallets`); Wallets gets a `#fef38b` pill background with a dark icon when `pathname === "/wallets"`. A dedicated `/wallets` page shows a Recharts donut of balance distribution (grouped by currency — currencies are never summed together) plus a single full balance grid — an earlier version duplicated this as two separate wallet lists (a vertical grid and a horizontal carousel); the carousel (`WalletList`) is no longer rendered there. The donut's container is constrained to `aspect-ratio: 1, max-width: 220px` so it can't clip regardless of the parent grid column's width, and the grid uses semantic `.wallets-donut-area`/`.wallets-grid-area` classes folded into the existing responsive breakpoints instead of inline `style={{gridColumn}}`. Still needed: dedicated category management (edit/archive), a transaction edit/delete view beyond the dashboard's recent-activity list. Known gap: a transfer only appears in the source wallet's activity feed, not the destination's (the destination's balance still updates correctly via the DB trigger, just not its visible feed) — revisit if that matters.
* Phase 3: Dashboard — partially done. `/dashboard` shows the selected wallet's real balance (from `wallets.balance_minor`, not a derived figure) plus a 12-month income/expense summary and spend chart scoped to that wallet, computed in `src/lib/dashboard/summary.ts`. Deviation from the original plan: the summary sums in the Node server layer after fetching rows (paginated, capped at 10,000, Zod-validated), not via SQL `SUM`/`GROUP BY`. Works correctly at personal-app scale; revisit if that matters later. No date-range filter yet. A dedicated `/transactions` page (`src/components/dashboard/transactions-view.tsx`) now sits alongside it: a period toggle (this month / last 30 days / all time), inflow/outflow summary pills, an **Upcoming expenses** card (below the pills, before the category breakdown — the next 3 active commitments due within 30 days, soonest first, past-due ones marked "Overdue" rather than excluded; a lightweight `getUpcomingCommitments()` in `src/lib/commitments/data.ts` fetches just the commitments query, not the wallets/categories `getCommitmentsData()` also loads for the full `/commitments` page, and fails soft — an empty list, never a page-blocking error — since a pending migration shouldn't alarm a secondary card), a by-category breakdown (expense/income tab, proportional meters, reusing the same single-currency-only rule the wallets donut chart already enforces — a note appears when other-currency wallets are excluded), and a filterable full ledger (search, type pills, wallet dropdown) with no 5-item truncation, unlike the dashboard's own embedded `TransactionList`. "All time" is bounded by the same trailing-12-month window `getDashboardData()` already fetches for everything else, not literal unbounded history — building a second, separately-paginated unbounded query wasn't worth it for a filter label. Category icons are chosen from a picker (`src/components/ui/icon-picker.tsx`, grouped via `CATEGORY_ICON_GROUPS` in `src/components/ui/category-icon.tsx`) when adding a category through "+ New category" in the transaction form; before this, `NewCategoryFields` called `createCategory` without an icon, so every user-created category (as opposed to the seeded defaults) silently fell back to the generic wallet icon in the dropdown and feed. The `categories.icon` column and `createCategory`'s icon parameter already existed from the wallets ledger migration, so no schema change was needed here.
* Phase 4: Recurring payments — partially done, as commitment tracking rather than the original generated-occurrences design. A `/commitments` page (`src/components/commitments/commitments-view.tsx`) covers two obligation shapes on one `recurring_rules` table: indefinite `subscription`s (billing cycle, next due date) and fixed-length `bnpl` installment plans (total/paid installment counts, a payoff deadline). Both are planning records only — `saveCommitment`/`changeCommitmentStatus`/`deleteCommitment` (`src/app/commitments/actions.ts`) never touch wallet balances or insert transactions; recording an actual payment is still a manual expense entry on `/transactions`. A Postgres trigger (`validate_recurring_commitment`, in `20260915010000_recurring_commitments.sql`) enforces BNPL invariants at the database level (paid ≤ total, the deadline falls on or after the last scheduled installment given the billing cycle) so a client bug can't silently save an inconsistent plan. Optimistic-concurrency guard: every update/delete carries the row's last-read `updated_at` in the `eq()` filter, so a stale edit (open in two tabs, or after another change) fails closed with "this commitment changed in another window" instead of silently overwriting. The page heading puts "+ Add commitment" beside the title in one row; "Back to transactions" is a small muted link above the eyebrow (not a pill competing visually with the yellow Add button — it originally sat as a second bordered pill directly under "+ Add commitment", reading as two stacked buttons). Each subscription/BNPL card's amount-and-actions block (`.subscriptionEnd`) had a real overflow bug on narrow screens: its mobile rule set `flex-basis: 100%` (claim the full card width) and `margin-left: 52px` (indent under the avatar) together, which doesn't shrink the box to fit — the margin pushes an already-full-width element another 52px right, so the trailing delete button rendered outside the card. Fixed by dropping the margin instead of trying to compute a matching `calc()` width, and added `overflow: hidden` to the card containers as a backstop. Still not started: generated per-occurrence rows or a reminder/notification beyond the transactions page's Upcoming expenses card.
* Phase 5: Wishlist — not started. CRUD with priority and status, "mark purchased" action that links to a transaction.
* Phase 6: Export — not started. CSV export of transactions.
* Settings and appearance (unplanned, added alongside Phase 4) — a `/settings` page (`src/components/settings/settings-view.tsx`) covers four cards: **Appearance** (light/dark/system via `next-themes`, persisted to `profiles.theme_preference` and re-applied on sign-in from any device by `ThemeProvider`'s `AccountThemeSync`, `src/components/theme-provider.tsx`); **Profile** (display name, backing the dashboard's "Hi, [name]" greeting); **Wallets** (inline rename, set default, delete — reusing `renameWallet`/`setDefaultWallet`/`deleteWallet` from `src/app/dashboard/actions.ts`, which now call `set_default_wallet`/`delete_managed_wallet` Postgres functions instead of doing the clear-then-set/list-then-delete sequence as separate client-visible statements, closing a race window between concurrent requests); **Categories** (rename, delete, and re-pick an icon via the same `IconPicker` grid used in "+ New category", tabbed by expense/income). Each wallet row's "Set as default"/Default-badge sits left-anchored against the rename/delete icon buttons on the right (`justify-content: space-between`, not everything crammed flex-end) so the row doesn't read as one undifferentiated cluster of controls; the page's bottom padding always includes `env(safe-area-inset-bottom)` (previously only added at a narrow-width breakpoint), bumped from 144px to 180px of base clearance (matching `/transactions`' and `/commitments`' shared `.transactions-page` padding) after a report of the nav still crowding the last card on a real device — measured directly in the browser at 375px and 412px afterward (scroll to true bottom, compare the last card's bottom edge to the nav's top edge) rather than trusting a screenshot, since a screenshot can't distinguish "still mid-scroll" from "physically blocked". Dark mode is CSS custom properties only (`--surface`, `--border`, `--color-ink`, etc. redefined under a `.dark` class in `globals.css`, matching `next-themes`' `attribute="class"` mode) — no Tailwind `dark:` variants were introduced in dashboard/wallets/transactions/settings/commitments code, keeping the "no Tailwind utility classes" rule intact for everything built under that rule; the pre-existing auth pages (`auth-form.tsx`, `auth-shell.tsx`) already used Tailwind before that convention existed and picked up matching `dark:` variants for consistency within those files only, not as a precedent for new code.

Backlog, explicitly out of scope unless asked: email or push reminders, receipt parsing, bank CSV import, AI-based categorization, multi-currency conversion beyond storing the code.

## Performance notes

* `getDashboardData()` (`src/lib/dashboard/data.ts`) fetches the first page of transactions concurrently with wallets/categories via one `Promise.all`, instead of awaiting wallets/categories first and only then starting the transactions query. That sequential wait was the real cause of slow dashboard/wallets loads, not missing indexes.
* Indexes on `wallets(user_id)`, `transactions(user_id, occurred_on desc)`, `transactions(wallet_id)`, and `categories(user_id)` were suggested again in a later task but already exist under different names from earlier migrations (`wallets_user_id_idx`, `transactions_user_occurred_on_idx`, `transactions_wallet_id_idx`, `categories_user_id_idx`) — check `supabase/migrations/` and the live schema before adding an index; a duplicate index costs write throughput for no read benefit.
* The repeated `supabase.auth.getUser()` calls across the request are now deduplicated (this was previously deferred). Every navigation used to pay for 2 serial `/auth/v1/user` round-trips (the proxy validating the session, then the page's data loader re-validating), and 3 on `/transactions` (proxy + `getDashboardData` + `getUpcomingCommitments`). That serial auth waterfall — not the DB queries, which were already parallel — was the dominant "1-2s until content" cost on a hobby-tier Supabase. Fix: the proxy already validates the JWT authentically on every matched request, so it now forwards the validated identity in request headers (`x-folio-uid`/`-email`/`-name`, `src/lib/auth/identity-headers.ts`) that it **always deletes before setting** (so a client can never inject them). Read-path data loaders call `getAuthedUser()` (`src/lib/auth/current-user.ts`) instead of `supabase.auth.getUser()`: it reads those headers (no network) and, only if they're absent, falls back to a real `getUser()` — so behaviour degrades to correct-but-slower, never broken. It's `cache()`d so `/transactions`' two loaders share one resolution. This is a latency change, not a trust change: the Supabase queries still carry the cookie JWT and stay RLS-gated, so even a (impossible, since the proxy overwrites) spoofed id would intersect RLS to zero rows rather than leak data. **Mutations (`dashboard/actions.ts`, `settings/actions.ts`, `commitments/actions.ts`) deliberately still call `getUser()` directly** — a write should validate authoritatively right before it runs, and they're not on the navigation hot path. The authenticated fast path could not be smoke-tested end-to-end here (no real session in this environment); the public/redirect proxy paths and the `getUser()` fallback were verified, and the fallback guarantees no breakage even if the header plumbing needs adjustment against the live account.
* `wallets/loading.tsx` and `wallets/error.tsx` were added, mirroring the existing `dashboard/loading.tsx` and `dashboard/error.tsx` pair, so the `/wallets` route gets the same Suspense-based skeleton and error boundary the dashboard already had.

## Security requirements (non-negotiable)

* No public registration route or sign-up form, ever. The owner account is provisioned out-of-band (admin API or dashboard).
* Enforce the email allowlist server-side, at session creation, never only in the UI
* RLS enabled on every table, no exceptions; verify a logged-out request returns no data
* `SUPABASE_SERVICE_ROLE_KEY` stays server-side only, never in client code or client bundles
* HttpOnly, Secure, SameSite cookies for session state, no tokens in localStorage
* Validate everything server-side with Zod, even where the client already validates
* Never log tokens, session cookies, or full transaction payloads
* Reasonable Content Security Policy, auth redirect URLs restricted to known origins

## Working style

* Explain key decisions briefly, especially trade-offs.
* Favor plain, explicit code over adding a framework or library to save a few lines. If a dependency is genuinely worth adding, say why before adding it.
* Keep commit messages and UI copy plain text: no em dashes, no emojis.
* Ask before making a schema change that is not in the plan above.
