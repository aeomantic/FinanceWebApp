# Folio (Personal Finance Webapp)

A personal finance webapp for a single user (me), called Folio: password-gated login, expense tracking, a wishlist, and recurring monthly payment tracking.

## Decided stack

* Frontend and backend: Next.js (App Router) with TypeScript
* Styling: Tailwind CSS is installed but the app doesn't use its utility classes — every component uses hand-authored CSS (`globals.css` for page-level/shared classes, a `components.module.css` per-directory for scoped ones), matching a specific soft-sage/warm-yellow palette defined as CSS custom properties. Match this palette and pattern for new UI; don't introduce Tailwind utility classes or a different color system.
* Database and auth: Supabase (Postgres, email/password auth through Supabase Auth, Row Level Security)
* Validation: Zod on all incoming form and API data, backed by database constraints
* Hosting: Vercel (Hobby plan) for the app, Supabase for the database and auth
* Charts: Recharts (`src/components/dashboard/wallet-distribution-chart.tsx` is the first real usage; `spend-chart.tsx` predates that decision and is hand-rolled SVG — leave it as is rather than migrating it speculatively)
* Icons: `lucide-react` for anything data-driven (category icons, looked up by a kebab-case string key stored in the database via `src/components/ui/category-icon.tsx`); the original hand-drawn SVG set in `src/components/ui/icon.tsx` stays for fixed chrome (nav, buttons) since it already matches the exact stroke width/style
* No UI component library (no Radix, no Headless UI): dialogs use the native `<dialog>` element (`src/components/ui/modal.tsx`), the custom dropdown (`src/components/ui/select.tsx`) is hand-rolled. Keep this pattern; a single-purpose UI library isn't worth the dependency at this app's size.

Do not propose alternative stacks or re-open this decision.

Auth history: originally planned as Google OAuth, then switched to Supabase magic link, then switched again to Supabase email/password. There is still no public registration: the single owner account is provisioned directly against Supabase (admin API or dashboard), never through a sign-up form. `/register` must not exist as a route.

## Prerequisites

1. A Supabase project with the Email provider enabled for password sign-in (no external OAuth provider needed)
2. A GitHub repository for the project (already set up: `github.com/aeomantic/FinanceWebApp`)
3. Environment variables in `.env.local` (gitignored, see `.env.example`):
   * `NEXT_PUBLIC_SUPABASE_URL`
   * `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   * `SUPABASE_SERVICE_ROLE_KEY` (server-only, never exposed to the client, not used by any request-serving code path — only for one-off admin scripts like provisioning the owner account)
   * `ALLOWED_EMAIL` (the only email allowed to log in)

## Data model

See `supabase/migrations/` for the schema as SQL migration files, applied in order. Do not apply schema changes by hand through the dashboard; commit a migration file instead. Migrations that need to land on the live project get pasted into the Supabase SQL Editor manually — there is no working CLI link to this project (the local `supabase` CLI login is tied to an unrelated project), and no DB password for a direct connection.

**The wallet-deletion fix now lives in `20260918030000_delete_wallet_safely.sql`, which is the one to apply (it is self-contained and supersedes `..000000` and `..020000`).** It re-asserts, by drop-by-discovery, every FK into `wallets(id)`/`transactions(id)` with the right action, recreates the `wallets`/`transactions` DELETE policies drift-proof, and creates `public.delete_wallet_safely(target_wallet_id uuid) returns jsonb` — a `SECURITY DEFINER` RPC (search_path empty, fully qualified) that does all unlinking, transaction cleanup, deletion, and default promotion in one transaction, bypassing child-table RLS while enforcing ownership itself (`caller = auth.uid()`, every statement scoped to `user_id = caller`). It returns `{success:false,error}` jsonb for handled cases (only-wallet) and raises for auth/ownership. **`deleteWallet` in `dashboard/actions.ts` now calls `delete_wallet_safely` (not the older `delete_managed_wallet`, which stays defined but unused) and surfaces the exact Postgres `error.message` to the UI plus `code`/`details`/`hint` to the console**, so any remaining constraint/RLS block is diagnosable instead of hidden. The file's header comment carries an `information_schema` discovery query to list every live FK referencing `wallets`; the committed schema has exactly three (transactions.wallet_id CASCADE, transactions.destination_wallet_id SET NULL, recurring_rules.wallet_id SET NULL) and no `recurring_occurrences.wallet_id`, `goals.wallet_id`, `budgets`, or profile default-wallet pointer, so the function is adapted to that reality (it never nulls a transfer's destination — that would violate the transfer check constraint — and never deletes recurring rules, only detaches them). Run the discovery query if deletion still fails after applying: an unexpected row there is an undocumented drifted FK to extend the function for.

**Also committed but possibly not yet applied: `20260918010000_goals_wishlist.sql`** (creates `goals`, adds `icon`/`converted_goal_id` to `wishlist_items`; confirmed applied from the owner's goals screenshots). The earlier `20260918000000` and `20260918020000` wallet-deletion attempts are kept for history but are fully superseded by `..030000`.

Running `..020000` alone is sufficient for the wallet-deletion fix; `..000000` is kept for history. The two `20260915*` migrations (settings, recurring commitments) are also applied — Settings and Commitments work against the live account.

Tables: `profiles`, `wallets`, `categories`, `transactions`, `wishlist_items`, `goals`, `recurring_rules`, `recurring_occurrences`.

The ledger is wallet-based (envelope style): every transaction moves money into, out of, or between wallets, not just into a category. This was a deliberate pivot from the original "categories on bare transactions" design (see `supabase/migrations/20260914053049_add_wallets_ledger_model.sql`).

* `wallets`: named balances (`balance_minor`) the owner tracks separately, e.g. "Everyday", "Food & Groceries", "Bills". Each has its own currency.
* `categories`: narrowed to `type` in (`expense`, `income`) — transfers are a transaction type now, not a category. Has `icon` for the picker UI, plus the original `color`/`is_archived`.
* `transactions`: `wallet_id` (required), `destination_wallet_id` (only for `type = 'transfer'`), `category_id` (nullable, `on delete set null`), `amount_minor` (positive magnitude, direction comes from `type`), `note` (replaces the old separate `merchant`/`notes` fields).
* A Postgres trigger (`sync_wallet_balance`) keeps `wallets.balance_minor` correct on every transaction insert/update/delete, so the balance is derived from the ledger rather than trusted from a second client-side write.
* RLS on `transactions` also verifies `wallet_id`/`destination_wallet_id`/`category_id` belong to the caller, not just `user_id` — otherwise a request could satisfy `user_id = auth.uid()` while still pointing at (and mutating the balance of) another user's wallet.
* `wallets.is_default` marks the one wallet the dashboard selects on load; a partial unique index (`wallets_one_default_per_user`, `where is_default`) enforces at most one per user at the database level. The first wallet a user creates becomes their default automatically (`createWallet` in `src/app/dashboard/actions.ts`); `setDefaultWallet` clears the old one before setting the new one, in that order, since a partial unique index only rejects two `true` rows, never zero.

**This project's live RLS policies have repeatedly not matched what the committed migration files assumed.** Phase 0's schema turned up already applied to the live project before any migration was run against it (never fully explained), and after the wallets migration landed, `transactions` INSERT, UPDATE, and SELECT policies plus all four `categories` policies turned out to be missing, misnamed, or otherwise not doing what the original migration specified — causing writes or reads to silently fail (no error, RLS just filters to zero rows) rather than throw. The fix pattern each time: `select policyname from pg_policies where schemaname = 'public' and tablename = '<table>'`, drop whatever actually exists via a `do $$ ... $$` block, recreate cleanly — never assume a policy exists under the name a migration file gives it. If something silently returns empty or a write silently no-ops against the live database, suspect RLS policy drift before anything else, and diagnose by reproducing the same operation with the service-role key (bypasses RLS) to isolate schema/payload issues from RLS issues.

Notes on the rest of the schema:

* Money is always an integer in minor units. `amount_minor = 1250` means SGD 12.50. Never use a float or JS number for stored money.
* Every table carries `user_id` even though there is one user. This keeps RLS simple and future-proofs the schema.
* A wishlist item links to a transaction only after purchase, through `purchased_transaction_id`. Wishlist and transactions stay separate: one is intent, the other is fact.
* Recurring payments follow a rule-plus-occurrences pattern, not full RRULE syntax. Five frequency values are sufficient for v1: weekly, monthly, quarterly, yearly, custom_months. Not started yet; when it is, decide how recurring bills interact with the narrowed category `type`.
* Row Level Security is enabled on every table, with policies restricting select, insert, update, and delete to rows where `user_id = auth.uid()`.

## Build order

Work through phases one at a time. After each phase, stop, summarize what was built, and wait for confirmation before starting the next one. (Note: a large chunk of Phase 2/3 landed in one uncoordinated pass outside this discipline — see status below. Return to one-phase-at-a-time from here forward.)

* Phase 0: Scaffolding — done. Next.js/TypeScript, Tailwind, Supabase clients (browser + server), env vars, repo pushed to GitHub.
* Phase 1: Authentication — done. Email/password sign-in through Supabase Auth (`/login`, `/forgot-password`, `/auth/reset-password`). Allowlist enforced server-side at session creation and re-checked on every request via the proxy, not just hidden in the UI. No registration route; the owner account is provisioned via the admin API.
* Phase 2: Wallets, categories, and transactions — partially done. `src/app/dashboard/actions.ts` has `createWallet`, `createCategory`, `setDefaultWallet`, `renameWallet`, `deleteWallet`, and a transfer-aware `recordTransaction` (expense/income/transfer, wallet-scoped, optional category, `note`). Category creation is available inline from the transaction form via a custom dropdown (`src/components/ui/select.tsx`), not a native `<select>`. A standard 10-expense/6-income category taxonomy was originally seeded automatically on first dashboard load whenever the account had zero categories; that auto-reseed was removed once Settings could delete categories (see below), since re-seeding on every empty read meant a deliberate "delete all categories" was silently undone on the next page load. `getDashboardData()` now reads categories as-is and never recreates them — dead code from that removal (`DEFAULT_CATEGORIES`/`src/lib/dashboard/default-categories.ts`) was deleted rather than left orphaned. This is safe for the single real account this app runs against (already seeded from earlier development); a genuinely fresh Supabase project would need categories added by hand or a new seeding path reintroduced deliberately. Every wallet card (in `WalletList` and the `/wallets` page's balance grid) has a three-dot action menu (`src/components/dashboard/wallet-card-menu.tsx`, built on a hand-rolled `role="menu"` component, `src/components/ui/dropdown-menu.tsx` — distinct from `select.tsx`'s listbox pattern since menu items trigger actions rather than binding a value): set/see default, rename, hide balance, delete. Deleting a wallet is a real, irreversible action — `transactions.wallet_id` is `on delete cascade`, so it takes every transaction on that wallet with it; `deleteWallet` refuses to delete a user's only wallet and auto-promotes another wallet to default first if the one being deleted was it. Per-wallet balance-hiding is a display preference, not account data, so it lives in localStorage (`src/lib/dashboard/use-hidden-wallets.ts`, via `useSyncExternalStore` so every mounted instance stays in sync and SSR gets a stable empty snapshot) rather than a database column. Wallet creation lives in one shared `AddWalletDialog` (`src/components/dashboard/add-wallet-dialog.tsx`), taking the trigger markup as a render prop (`children: (open) => ReactNode`) so `WalletList`'s "+" tile and the `/wallets` grid's full-width "Add wallet" card share the same form/validation logic; it opens/closes via `isOpen` state plus a `useEffect` calling `showModal()`/`close()` (matching `modal.tsx`'s pattern) rather than an imperative ref call from the trigger callback, since the latter tripped the `react-hooks/refs` rule (a ref-closing closure passed into a render prop can't be proven safe from render-time access). The horizontal wallet carousel (`WalletList`, used on `/dashboard`) hides its scrollbar cross-browser (`scrollbar-width: none`, `-ms-overflow-style: none`, `::-webkit-scrollbar { display: none }` — the earlier `scrollbar-width: thin` left a visible thumb cutting across the bottom of the cards) and widens each card to a 170px minimum with a wrapping (not truncating) name, so names like "Food & Groceries" render in full instead of ellipsizing to "Food & Groceri...". The three-dot menu is a real `<button>` for wallet selection plus a separately absolutely-positioned `WalletCardMenu` in the corner, rather than the whole card being one clickable surface with the menu nested awkwardly inside it. The bottom mobile nav is a single shared `MobileNav` component (`src/components/dashboard/mobile-nav.tsx`), used by both the dashboard shell and the wallets page, with active-state styling keyed off `usePathname()`: Home is a solid black circle whose house icon turns `#fef38b` when active (i.e. not on `/wallets`); Wallets gets a `#fef38b` pill background with a dark icon when `pathname === "/wallets"`. A dedicated `/wallets` page shows a Recharts donut of balance distribution (grouped by currency — currencies are never summed together) plus a single full balance grid — an earlier version duplicated this as two separate wallet lists (a vertical grid and a horizontal carousel); the carousel (`WalletList`) is no longer rendered there. The donut's container is constrained to `aspect-ratio: 1, max-width: 220px` so it can't clip regardless of the parent grid column's width, and the grid uses semantic `.wallets-donut-area`/`.wallets-grid-area` classes folded into the existing responsive breakpoints instead of inline `style={{gridColumn}}`. Transaction rows in both feeds (the dashboard's `TransactionList` and the `/transactions` ledger) are clickable and open `TransactionDetailDialog` (`src/components/dashboard/transaction-detail-dialog.tsx`), which is how a stored `note` is read back - before this the note was persisted but had no surface anywhere in the UI. It shows the amount (tinted green for income, neutral for a transfer), the transaction date, the recorded timestamp, category, wallet (From/To for transfers, and no category row since transfers don't carry one), a type badge, and a dedicated note card that falls back to "No note added". Two date fields are deliberately distinguished: `occurred_on` is date-only and is formatted at UTC noon (the same guard the feed's date headings use, so a timezone can never shift the day), while `created_at` is a real instant surfaced as `recordedAt` and formatted in the reader's local timezone. `created_at` was already on the table from the init schema and survived the wallets pivot (that migration only altered columns), so it needed adding to the select, not a schema change. Rows are real `<button>` elements rather than `role="button"` divs (free Enter/Space handling, matching the direction `wallet-list.tsx` already moved in); the visual rules stay on `.transactionRow` and only `.transactionRowButton` adds the button resets, so the non-interactive rows that also use `.transactionRow` (the upcoming-expenses list) never pick up a misleading pointer cursor. The dialog reuses the native-`<dialog>` `Modal`, which gained an optional `className` so it can opt into `.app-modal.modal-sheet` - a bottom-pinned sheet under 680px (two classes so it reliably beats `.app-modal`'s centred margin) and the normal centred modal above that. Transaction editing is now built: the detail dialog's Edit button opens the same form used for recording (extracted to `src/components/dashboard/transaction-form.tsx`, shared by `dashboard-shell.tsx` and `transactions-view.tsx`) prefilled with the row's values, plus a source-wallet selector that only renders in edit mode. `updateTransaction` in `dashboard/actions.ts` is a plain RLS-gated row update with `currency` reassigned from the (possibly new) source wallet — no client-side balance delta math exists to get wrong, because `sync_wallet_balance` already handles UPDATE by reversing the OLD row's effect (source and destination) and applying the NEW row's, covering wallet moves. The transaction's `type` is deliberately not editable (changing income to transfer mid-edit drags category/destination semantics along for no real use case; record a new transaction instead). The transfer-wallet rules live in one shared `.check()` callback (`checkTransferWallets` in `src/lib/dashboard/validation.ts`) so the record and update schemas can never drift. Still needed: dedicated category management (edit/archive), and transaction delete - it needs a verified `transactions` DELETE policy, which is its own phase given how often this project's live RLS has drifted from the migrations. Known gap: a transfer only appears in the source wallet's activity feed, not the destination's (the destination's balance still updates correctly via the DB trigger, just not its visible feed) — revisit if that matters.

* Phase 4: Recurring payments — partially done, as commitment tracking rather than the original generated-occurrences design. A `/commitments` page (`src/components/commitments/commitments-view.tsx`) covers two obligation shapes on one `recurring_rules` table: indefinite `subscription`s (billing cycle, next due date) and fixed-length `bnpl` installment plans (total/paid installment counts, a payoff deadline). Both are planning records only — `saveCommitment`/`changeCommitmentStatus`/`deleteCommitment` (`src/app/commitments/actions.ts`) never touch wallet balances or insert transactions; recording an actual payment is still a manual expense entry on `/transactions`. A Postgres trigger (`validate_recurring_commitment`, in `20260915010000_recurring_commitments.sql`) enforces BNPL invariants at the database level (paid ≤ total, the deadline falls on or after the last scheduled installment given the billing cycle) so a client bug can't silently save an inconsistent plan. Optimistic-concurrency guard: every update/delete carries the row's last-read `updated_at` in the `eq()` filter, so a stale edit (open in two tabs, or after another change) fails closed with "this commitment changed in another window" instead of silently overwriting. The page heading puts "+ Add commitment" beside the title in one row; "Back to transactions" is a small muted link above the eyebrow (not a pill competing visually with the yellow Add button — it originally sat as a second bordered pill directly under "+ Add commitment", reading as two stacked buttons). * Goals and wishlist (added alongside Phase 5) — now **two dedicated routes**, `/goals` (`src/components/goals/goals-view.tsx`, savings targets only) and `/wishlist` (`src/components/goals/wishlist-view.tsx`, wants only). They were briefly one combined tabbed page; the tab was split into separate routes per an explicit request, and both are reachable from the desktop side-rail (a new `target` icon in `src/components/ui/icon.tsx`) and top-nav, from cross-links on each page, and from the dashboard bento cards. Both pages call the same `getGoalsData()` and render their half. Goals (`public.goals`, created by `20260918010000_goals_wishlist.sql`) are savings targets: integer minor units (`target_minor`/`saved_minor` bigint, never numeric), own currency, optional deadline and picker icon. Wishes reuse the existing `wishlist_items` table (the migration adds `icon` and `converted_goal_id`; the loaders show `status = 'active'` rows). The FK is ON DELETE SET NULL on purpose: deleting a goal returns its wish to a convertible state instead of stranding a stale "converted" flag. Wish prices display in the default wallet's currency because the init-schema table has no currency column. The four dialogs live in `src/components/goals/goal-dialogs.tsx` sharing one `useDialogSubmit` hook (busy ref + transition + refresh-then-close, the CommitmentDialog pattern). The dashboard (`DashboardShell`) shows a **Goals summary card** (top goals with progress meters + "View all goals") and a **Wishlist preview card** (recent wants + "Manage wishlist") in the wallets-area bento, fed by a soft-failing `getGoalsSummary()` (`src/lib/goals/data.ts`, empty on any error like `getUpcomingCommitments`) and rendered by `src/components/dashboard/goals-preview.tsx`; the old "Plan your goals" text-action on the insight card was replaced by these cards, and `/preview` shows them with demo data.

Backlog, explicitly out of scope unless asked: email or push reminders, receipt parsing, bank CSV import, AI-based categorization, multi-currency conversion beyond storing the code.

## Performance notes

* `getDashboardData()` (`src/lib/dashboard/data.ts`) fetches the first page of transactions concurrently with wallets/categories via one `Promise.all`, instead of awaiting wallets/categories first and only then starting the transactions query. That sequential wait was the real cause of slow dashboard/wallets loads, not missing indexes.
* Indexes on `wallets(user_id)`, `transactions(user_id, occurred_on desc)`, `transactions(wallet_id)`, and `categories(user_id)` were suggested again in a later task but already exist under different names from earlier migrations (`wallets_user_id_idx`, `transactions_user_occurred_on_idx`, `transactions_wallet_id_idx`, `categories_user_id_idx`) — check `supabase/migrations/` and the live schema before adding an index; a duplicate index costs write throughput for no read benefit.
* The repeated `supabase.auth.getUser()` calls across the request are now deduplicated (this was previously deferred). Every navigation used to pay for 2 serial `/auth/v1/user` round-trips (the proxy validating the session, then the page's data loader re-validating), and 3 on `/transactions` (proxy + `getDashboardData` + `getUpcomingCommitments`). That serial auth waterfall — not the DB queries, which were already parallel — was the dominant "1-2s until content" cost on a hobby-tier Supabase. Fix: the proxy already validates the JWT authentically on every matched request, so it now forwards the validated identity in request headers (`x-folio-uid`/`-email`/`-name`, `src/lib/auth/identity-headers.ts`) that it **always deletes before setting** (so a client can never inject them). Read-path data loaders call `getAuthedUser()` (`src/lib/auth/current-user.ts`) instead of `supabase.auth.getUser()`: it reads those headers (no network) and, only if they're absent, falls back to a real `getUser()` — so behaviour degrades to correct-but-slower, never broken. It's `cache()`d so `/transactions`' two loaders share one resolution. This is a latency change, not a trust change: the Supabase queries still carry the cookie JWT and stay RLS-gated, so even a (impossible, since the proxy overwrites) spoofed id would intersect RLS to zero rows rather than leak data. **Mutations (`dashboard/actions.ts`, `settings/actions.ts`, `commitments/actions.ts`) deliberately still call `getUser()` directly** — a write should validate authoritatively right before it runs, and they're not on the navigation hot path. The authenticated fast path could not be smoke-tested end-to-end here (no real session in this environment); the public/redirect proxy paths and the `getUser()` fallback were verified, and the fallback guarantees no breakage even if the header plumbing needs adjustment against the live account.
* `wallets/loading.tsx` and `wallets/error.tsx` were added, mirroring the existing `dashboard/loading.tsx` and `dashboard/error.tsx` pair, so the `/wallets` route gets the same Suspense-based skeleton and error boundary the dashboard already had.

## Security requirements (non-negotiable)

* No public registration route or sign-up form, ever. The owner account is provisioned out-of-band (admin API or dashboard).
* Enforce the email allowlist server-side, at session creation, never only in the UI
* RLS enabled on every table, no exceptions; verify a logged-out request returns no data
* `SUPABASE_SERVICE_ROLE_KEY` stays server-side only, never in client code or client bundles
* HttpOnly, Secure, SameSite cookies for session state, no tokens in localStorage
* Validate everything server-side with Zod, even where the client already validates
* Never log tokens, session cookies, or full transaction payloads
* Reasonable Content Security Policy, auth redirect URLs restricted to known origins
